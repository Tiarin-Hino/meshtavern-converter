## 2. Decisions

### 2.1 Where the theme files live _(the PM decides; this pass recommends A)_

**A. A copy here, the application the source** (the spec's proposal). `public/theme/` holds `tokens.css`, `components.css`, `theme.js`, `fonts/` (the two WOFF2 files and the two OFL texts) and `LICENSE-Lucide.txt`, byte for byte the application's `web/public/theme/` files of the same names; Vite copies `public/` into `dist/`, so the page serves them at `/theme/` as the application does. A `README.md` beside them names the application's commit they came from. The application's `web/src/theme-files.test.ts` gains one case: every file of that list in `node_modules/meshtavern-converter/public/theme/` equals its own, byte for byte, so a change made in the application fails there until the pin is bumped, which is the signal; this repo never edits them by hand (a check here, `src/theme-files.test.ts`, keeps the budgets and the locality of the copy, section 8). Not copied: `pages.css` (the page does not link it; the app bar's and the card's measurements are in `mock.css`), the favicon and the app icon (K6 makes this page's own), `NOTICE.txt` (K4 writes this page's own, which lists what this page ships).

**B. This library the source, the application imports.** `package.json` exports `./theme/*`; the application's build copies them from `node_modules` into `web/dist/theme/`, its server serves them as today, and the equality test goes.

The trade:

|                                               | A: a copy here, the application the source                                                                                                                      | B: the library the source                                                                                                                                                                                                                |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Copies                                        | Two, kept equal by a test; a day's drift possible after a change in the application until the pin is bumped                                                     | One                                                                                                                                                                                                                                      |
| Where the design system is decided            | In the application, with its style guide, its contrast check, its per-system theme seam (`themes.css`), its 71 icons, its wordmark: all stay where they are     | Split: the tokens and components here, the guide, the seam, the icons and the mark there; or everything moves, and the public MIT repo carries the table's treatments (`--turn`, `--hp-*`, `--private`), which mean nothing on this page |
| A change to the look                          | One PR in the application; this repo takes it with the next pin bump, which the application makes anyway for the engine                                         | One PR here, a merge, a pin bump, then the application sees it: the cost spec 10 accepted for the engine, but the application's epic #220 changes the look far more often than the engine changes                                        |
| A new role this page needs                    | Added in the application first (spec L4 says so already), then the bump                                                                                         | Added here                                                                                                                                                                                                                               |
| What the library's views need from a consumer | To link `tokens.css` and `components.css` (their own copy or this package's) before `questions.css` and `painting.css` (section 5); the same under both options | The same                                                                                                                                                                                                                                 |

Recommendation: **A**. The design system is the application's product, its tooling lives there, and the library's two views only need a consumer that links the two stylesheets, which the application does already. The application's test is a one-case change and the pin bump exists for the engine. _(proposal)_

### 2.2 Both themes: the page follows the system and has the switch; the scene stays dark _(proposal, the spec's P kept)_

- `index.html` loads `/theme/theme.js` in its head before the stylesheets, as the application's server pages do: the page paints in the stored choice at once, and the switch (`[data-theme-switch]`, rendered `hidden`, shown by the script) is the application's `.segmented` group of three icon buttons named Light, Dark and System with `data-theme-choice`, `aria-pressed` on the current one. `mt-theme` in `localStorage` holds `light` or `dark`; the system's setting is no entry. The script is a byte-equal copy (2 KB); the page needs no TypeScript for the theme. The spec's data line already allows "the theme" among the person's own choices kept on the device; nothing is sent, and `e2e/promise.spec.ts` keeps proving it.
- **The viewport, the question scene and the painting scene are dark in both themes**: they read `--scene-backdrop` and `--scene-grid`, which the application defines as the scene's roles, always dark, because the table is always dark. The mini's look was tuned on a dark backdrop (the corpus's comparison sheets, every look preset), the thumbnails are transparent, and the application's dialogs will show the same scene on its light pages. The light theme is therefore a light chrome around a dark stage (see `shots/page-done-desktop-light.png`). The one-line alternative, if the PM prefers a light stage: the page overrides `--scene-backdrop: var(--surface-sunken)` and `--scene-grid: var(--line-strong)` in its own stylesheet and the scenes follow; the mini's look then needs a second judgement on light. _(proposal)_
- **Dark only** is the other line the spec allows: `<html data-theme="dark">` and no switch. Everything else in this note stands either way.
- The costs of the switch: the script, the three buttons, and in K5 every reference screenshot and every scan twice. The light theme adds no colour: every pair the page shows is one the application's contrast check already measures.

### 2.3 Stylesheets: who holds what

- **`index.html`** links `/theme/tokens.css` and `/theme/components.css`, then Vite's bundle of `src/page/style.css` (the page's own, after the components so it wins where both style a thing), and loads `/theme/theme.js` in the head. `e2e/promise.spec.ts` allows `/theme/` beside `/assets/` and `/basis/`: a font is fetched when the first glyph of its face is drawn, which can be after the file is picked.
- **`src/page/style.css`** holds the page's layout only: the frame (the bar, the stage, where the card and the panel sit, the sheet, the chips, the drag overlay), the disclosure (section 4.4), the page's copy of the callout (section 4.3), the `?dev` tools' few rules (section 6), and no colour literal, no control rule, no element rule. Its `:root` block with the ten custom properties goes (section 3). What is today the generic `button, select, input[type='number']` rule goes: every control carries a component class.
- **`src/lib/questions.css`** holds the question view's layout only: the scene host, the view's own panel (when no controls element is given), the sections' stacking and the pairs' colours. Its control rules go, because **the view's template carries the component classes** (`btn`, `btn-primary`, `btn-sm`, `btn-icon`, `btn-group`, `segmented`, `input`, `field`, `field-row`, `check`, `chip`, `chip-dot`, `panel-section`, `panel-footer`, `hint`; section 4.5), so the view is built on `components.css` as the spec's L1 says, and looks the same on the page and in the application without a bridge. The `--q-*` block goes (section 3). The consumer's contract, in the README: link `tokens.css` and `components.css` (its own copy or this package's `public/theme/`) before `questions.css`; the application does. The application's `.import-stop` bridge (`--panel: var(--surface-raised)` and the three others, `web/src/style.css`) is then dead and goes with the pin bump.
- **`src/lib/painting.css`** stays three rules; the cursor ring reads `--accent` (section 3).
- A rule the page needs that `components.css` does not have (the disclosure, the callout outside the application's page frames) is the page's own, in `style.css`, and is named in section 12 as a candidate for the application's component file.

### 3.1 The scenes' colours

The viewer (`src/page/viewer.ts`), the question scene (`src/lib/questions/scene.ts`) and the painting scene (`src/lib/painting/scene.ts`) each hold `0x1b1d22` for the background and `0x4a4f5a`, `0x2c3038` for the grid. They take them from one module, `src/lib/three/scene-colours.ts` _(proposal)_:

```ts
export interface SceneColours {
  backdrop: number; // --scene-backdrop
  gridCentre: number; // --scene-grid composited over the backdrop
  gridLine: number; // --scene-grid at half its alpha, composited over the backdrop
}
/** The values of tokens.css, pinned by a test; what a scene gets where no root carries the roles. */
export const SCENE_COLOURS_FALLBACK: SceneColours;
/** Reads the two roles from the root's computed style once; the fallback where a role is missing. */
export function readSceneColours(root: Element = document.documentElement): SceneColours;
```

A `THREE.GridHelper` takes two opaque colours, and `--scene-grid` is white at 16 % alpha: the module composites it over the backdrop for the centre lines and at half the alpha for the other lines, which keeps today's two-tone grid. Each scene reads the colours once in its constructor, as the application's `TableView` does; a theme change after that restyles the chrome but not the scene, which is right since the scene is dark in both themes (2.2). The module also holds `PAIR_COLOURS` (moved from the question scene), the thumbnail's lights (`0xffffff`, `0x30343c`) and `BLACK` for the clear colours, so that it is the one file of `src/lib/three/` the colour check allows; the look presets' coats (`look.ts`) and the painter's default colour (`#b03030`, `mount.ts`, moved to `brush.ts` beside `DEFAULT_BRUSH`) are paint, not chrome, and are allowed where they are. `baked-material.ts`'s material white becomes `new THREE.Color(1, 1, 1)`.
